Главный вывод для рейтинга: **нативная таблица лидеров Яндекса не удовлетворяет требованию «не доверять клиентскому JavaScript»** — очки записывает клиент, сервер разработчика в цепочке не участвует. Также она показывает имя Яндекс-профиля, а не игровой никнейм. Поэтому авторитетный рейтинг должен вестись на собственном сервере, а Яндекс используется как поставщик проверяемой личности игрока.

## 1. Рекомендуемый технологический стек

| Слой | Выбор | Обоснование |
|---|---|---|
| Язык | **TypeScript** (strict) | Контент-схемы, события и сохранения — места, где типы предотвращают ошибки. Ядро и сервер используют один и тот же код валидации рецептов. |
| Сборка | **Vite** | Быстрая разработка, хешированные ассеты, относительные пути (`base: './'`) для работы из архива, минимальная конфигурация. |
| Рендеринг | **DOM + CSS** (Pointer Events, CSS transforms), при необходимости тонкий `<canvas>`-слой для частиц | Игра преимущественно интерфейсная: тексты, списки, поиск, энциклопедия, дневник, локализация, адаптивная вёрстка. DOM даёт это бесплатно: качественный текст и кириллица, прокрутка, доступность, CSS-анимации, медиазапросы. Одновременно на поле — десятки объектов, а не тысячи, производительности DOM достаточно. |
| UI-фреймворк | **Без фреймворка** на старте: небольшой реактивный store + модули представлений | Поле с перетаскиванием всё равно управляется императивно. Экранов немного. Экономия 40–150 КБ и отсутствие лишней абстракции. Если интерфейс разрастётся, точечно подключается Preact (~4 КБ) без переписывания ядра. |
| Тесты | **Vitest** (unit), **Playwright** (e2e, эмуляция мобильных устройств и touch) | Chromium уже установлен в среде. |
| Валидация контента | **zod** (только в инструментах сборки и на сервере) + собственный граф-валидатор | Не попадает в клиентский бандл. |
| Сервер рейтинга | Бессерверные функции на TypeScript + SQL-хранилище; платформа — **решение пользователя** (см. §6, §7) | Логика проверки — общая с клиентом (модуль `core`). |
| Локальная проверка | `@yandex-games/sdk-dev-proxy` | Официальный инструмент, подставляет реальную CSP. |

**Почему не Phaser / PixiJS / Cocos.** Это движки для сцен с большим числом спрайтов. Для текстоёмкой головоломки они добавляют 300 КБ – 1 МБ, усложняют текст, прокрутку, локализацию и адаптивность. Преимущество Canvas (тысячи объектов, шейдеры) здесь не используется.

**Почему не React.** Перетаскивание на поле требует прямой работы с DOM; виртуальный DOM здесь мешает. Остальные экраны просты.

**Бюджеты производительности (критерии, не обещания):** начальный JS ≤ 150 КБ gzip; первый экран ≤ 3 МБ загрузки; архив целиком — ориентир ≤ 30 МБ при лимите 100 МБ; 60 fps при перетаскивании на среднем Android.

## 3. Архитектура игровой механики

### 3.1 Ядро алхимии (`core/alchemy`)

- **Индекс рецептов** строится один раз при загрузке: `Map<pairKey, Recipe>`.
  - Неупорядоченный ключ: идентификаторы сортируются → `"fire|water"`. Поэтому «Вода + Огонь» и «Огонь + Вода» — один рецепт.
  - Упорядоченный рецепт (`ordered: true`): ключ `"a>b"`. Поиск сначала по упорядоченному ключу, затем по неупорядоченному.
  - Поддерживается комбинация элемента с самим собой (`"water|water"`).
- **Детерминизм.** Одна пара → один рецепт → фиксированный результат. Валидатор запрещает две разные записи на одну пару. Рецепт может давать список результатов (1..N) — порядок фиксирован, набор всегда одинаковый.
- **`combine(state, a, b)`** — чистая функция, возвращает:
  - `{ kind: 'new', recipe, newElements }` — открыт хотя бы один новый элемент;
  - `{ kind: 'newRecipe', recipe }` — элемент известен, но найден новый способ его получения (альтернативный рецепт);
  - `{ kind: 'known', recipe }` — ничего нового;
  - `{ kind: 'none' }` — комбинация не существует.
- **Применение результата** (`core/progress`) обновляет `discoveredElements` (множество, повтор не увеличивает счёт), `foundRecipes`, порядковые номера открытий, и испускает доменные события `ElementDiscovered`, `RecipeFound`, `JournalEntryUnlocked`.
- Секретные элементы не учитываются в отображаемом «всего элементов», пока не найдены; в рейтинге считаются как обычные уникальные открытия.

### 3.2 Шина событий и подписчики

`main.ts` связывает: событие открытия → UI (анимация, карточка нового элемента) → сохранение (отложенная запись) → дневник (проверка условий) → онлайн-очередь (событие для сервера) → звук. Ядро не знает о подписчиках, что упрощает тесты и сервер.

### 3.3 Рабочее поле и перетаскивание (`ui/workspace`)

- **Pointer Events** + `setPointerCapture` — одна реализация для мыши, сенсора и пера. `touch-action: none` на поле и палитре, чтобы жест не прокручивал страницу.
- Порог начала перетаскивания (~6 px) отличает касание от перетаскивания.
- Сценарии: палитра → поле (создаётся экземпляр), поле → поле (перемещение или соединение), поле → палитра/корзина (удаление экземпляра), двойное касание — копия.
- **Альтернатива без перетаскивания:** коснуться элемента A, затем B — соединение. Это нужно для маленьких экранов и доступности.
- Попадание при отпускании — по пересечению с центром ближайшего экземпляра (с допуском), а не по точному `elementFromPoint`.
- Экземпляры на поле: `{ instanceId, elementId, x, y }` в нормализованных координатах, чтобы поворот экрана не ломал раскладку.
- Ограничения платформы: отключить выделение текста, контекстное меню, «резиновую» прокрутку страницы, масштабирование жестом.

### 3.4 Компоновка экрана

- **Портрет (телефон):** поле сверху, палитра — выдвижная нижняя панель с поиском и фильтром категорий.
- **Ландшафт / ПК:** палитра — боковая колонка, поле — основная область.
- Энциклопедия, дневник, рейтинг, настройки — полноэкранные «страницы книги» поверх поля.
- Проверяемые размеры: 360×640, 390×844, 412×915, 768×1024, 1024×768, 1366×768, 1920×1080.

### 3.5 Жизненный цикл и платформа

- `YaGames.init()` → загрузка контента и сохранения → отрисовка первого экрана → `LoadingAPI.ready()`.
- `GameplayAPI.start()` при активной игре, `stop()` — при открытии меню и рекламы.
- `game_api_pause` → заглушить звук и остановить анимации; `game_api_resume` → восстановить.
- `Platform` — интерфейс, поэтому игра запускается и тестируется без SDK (`platform/local`).

## 4. Архитектура контента и рецептов

### 4.1 Схемы

```jsonc
// content/elements/primal.json
[
  { "id": "water", "category": "primal", "art": "water", "starting": true },
  { "id": "steam", "category": "vapors", "art": "steam" },
  { "id": "philosophers_stone", "category": "great_work", "art": "philosophers_stone",
    "secret": true, "final": true }
]

// content/recipes/basics.json
[
  { "in": ["water", "fire"], "out": ["steam"] },
  { "in": ["earth", "fire"], "out": ["lava"] },
  { "in": ["mercury", "sulfur"], "out": ["cinnabar"], "ordered": true, "secret": true }
]

// content/journal/chapter1.json
[
  { "id": "page_001", "kind": "page",   "unlock": { "discoveries": 10 } },
  { "id": "margin_steam", "kind": "margin", "unlock": { "element": "steam" } },
  { "id": "formula_01", "kind": "formula", "unlock": { "all": [ { "element": "salt" }, { "element": "mercury" } ] } }
]

// content/locales/ru/elements.json
{ "steam": { "name": "Пар", "desc": "Вода, принявшая форму духа..." } }
```

- **Элемент:** `id` (латиница, snake_case, **неизменяем после выпуска**: на него ссылаются сохранения и сервер), `category`, `art`, `starting?`, `secret?`, `final?` (из него ничего не создаётся — для подсказок «тупик»), `tags?`.
- **Тексты** (название, описание) — в файлах локализации по `id`, отдельно от структуры. Добавление языка не трогает структуру контента.
- **Несколько рецептов для одного результата** — просто несколько записей с одинаковым `out`.
- **Переименование элемента** после выпуска — через карту `aliases` (`old_id → new_id`) и миграцию сохранений.
- **Версия контента** (`contentVersion`, хеш) встраивается в сборку и в серверную копию.

### 4.2 Компиляция

`tools/content-build.ts` собирает каталог `content/` в один компактный JSON (элементы, рецепты, журнал, хеш). Тот же файл получает сервер. Добавление элемента или рецепта = правка JSON и локализации; движок не меняется.

### 4.3 Валидатор (`core/validation` + `tools/content-check.ts`)

Ошибки (сборка падает):

1. Дубликаты `id` элементов и записей дневника.
2. Ссылки на несуществующие элементы во входах и выходах рецептов, в `unlock` дневника, в `aliases`.
3. Две записи на одну и ту же пару (с учётом правил порядка) — нарушение детерминизма.
4. Элемент без рецептов получения, если он не `starting`.
5. **Недостижимые элементы.** Вычисляется неподвижная точка: начинаем с `starting`, повторно применяем все рецепты, у которых оба входа уже достижимы, до стабилизации. Всё, что не достижимо, — ошибка. Этот же алгоритм ловит **циклы без начального пути**: элементы, получаемые только друг из друга, никогда не попадут в достижимое множество.
6. Рецепт порождает элемент без определения (нет в списке элементов).
7. Отсутствует название или описание на любом обязательном языке.
8. Отсутствует файл иллюстрации (с режимом «заглушка разрешена» на ранних этапах).

Предупреждения: рецепт создаёт начальный элемент; рецепт `a + b → a` (результат совпадает с входом); элемент-«тупик» без пометки `final`; категория без элементов.

Отчёт: число элементов по категориям, минимальная глубина каждого элемента (число шагов от старта), самые глубокие цепочки — помогает балансировать кривую сложности.

## 5. Сохранения

Три независимых уровня с разными задачами.

| Уровень | Где | Что | Для кого | Роль |
|---|---|---|---|---|
| Локальный | `localStorage` | Полный снимок прогресса и настроек, очередь событий для сервера | Все | Основной, работает без сети |
| Облачный | Яндекс `player.setData` (≤ 200 КБ) | Тот же снимок | Авторизованные | Перенос между устройствами, восстановление после очистки браузера |
| Серверный | Сервер рейтинга | Только подтверждённые открытия, никнейм | Авторизованные | Авторитетный источник рейтинга; дополнительный источник восстановления открытий |

### 5.1 Формат снимка

```ts
interface SaveV1 {
  v: 1;                        // версия схемы, для миграций
  contentVersion: string;
  updatedAt: number;           // клиентское время, только для настроек
  discovered: string[];        // id в порядке открытия
  recipes: string[];           // ключи найденных рецептов
  journal: { unlocked: string[]; read: string[] };
  settings: { lang?: string; sound: number; music: number; reducedMotion: boolean };
  profile: { nickname?: string };
  workspace?: { id: string; x: number; y: number }[];
  outbox: PendingEvent[];      // события, ещё не принятые сервером
}
```

Оценка размера: 1000 элементов × ~15 байт + рецепты ≈ 30–50 КБ — с запасом укладывается в 200 КБ.

### 5.2 Правила

- **Запись:** отложенная (≈1 с после изменения), принудительная — на `visibilitychange` / `pagehide`. Облачная запись — реже (по событию открытия с объединением в пачку и при сворачивании), с учётом лимитов частоты.
- **Слияние без потерь.** Открытия, рецепты и записи дневника только растут, поэтому объединяются как множества (объединение не может потерять открытие). Настройки — по последнему `updatedAt`. Это делает безопасной любую последовательность «локально → облако → другое устройство».
- **Загрузка:** локальный снимок → (если авторизован) облачный → слияние → (если доступен сервер) объединение с подтверждёнными сервером открытиями → запись результата обратно.
- **Повреждённые данные:** ошибка разбора не обнуляет прогресс молча: исходная строка сохраняется в резервный ключ, игрок получает понятное сообщение; используется облачная копия при наличии.
- **Миграции:** последовательные функции `v1 → v2 → ...`, покрытые тестами.
- **Неавторизованный игрок:** только локальное сохранение, игра полностью доступна. Предложение войти — ненавязчиво (для облака и рейтинга). После входа локальный прогресс сливается с облачным.
- **Офлайн:** алхимия, энциклопедия, дневник работают без сети; недоступность облака и рейтинга отображается индикатором, но ничего не блокирует.

## 6. Онлайн-рейтинг

### 6.1 Сравнение вариантов

| | A. Нативные таблицы Яндекса | B. Свой сервер + личность Яндекса (рекомендуется) |
|---|---|---|
| Запись очков | Клиентом, без участия сервера | Сервером после проверки событий |
| Защита от накрутки | Нет (любой клиент запишет любое число) | Есть: проверка рецептов, цепочек, частоты, идемпотентность |
| Отображаемое имя | Имя Яндекс-профиля | Игровой никнейм, меняется без потери прогресса |
| Ежедневные испытания | Только отдельными таблицами из консоли, без проверки | Серверная модель с датой и правилами |
| Стоимость и сопровождение | Бесплатно, без сервера | Сервер, база, развёртывание |
| Зависимости | — | Секретный ключ (требует подключения покупок), разрешение хоста в CSP |

Вариант A не выполняет обязательные требования проекта (серверная проверка, свой никнейм), поэтому в качестве авторитетного рейтинга не подходит. Его можно добавить позже как дополнительную, явно неавторитетную витрину — решение не обязательно сейчас.

### 6.2 Идентификация

1. Клиент: `ysdk.getPlayer({ signed: true })`; рейтинг доступен только авторизованным (`isAuthorized()`), неавторизованным предлагается `auth.openAuthDialog()`.
2. Клиент отправляет `signature` на `POST /auth/exchange`.
3. Сервер проверяет подпись секретным ключом игры (HMAC, алгоритм — сверить с официальным примером), извлекает `uniqueID`.
4. Сервер находит или создаёт запись `players` по `yandex_uid` (уникальный индекс) и выдаёт **собственный сессионный токен** (подписан серверным секретом, срок жизни ≈ 24 ч). Повторно запрашивать подпись при каждом запросе нельзя из-за лимита 20 запросов / 5 минут.
5. Внутренний `player_id` (UUID) стабилен. **Никнейм** — отдельное поле: смена никнейма не создаёт игрока и не трогает прогресс.

Никнейм: 3–20 символов, кириллица/латиница/цифры/пробел/дефис, нормализация Unicode, фильтр нецензурной лексики, ограничение частоты смены (например, раз в сутки). По умолчанию — имя Яндекс-профиля или «Безымянный алхимик №…».

### 6.3 Модель данных (SQL)

```
players(id uuid pk, yandex_uid text unique not null, nickname text, nickname_changed_at,
        score int not null default 0, score_reached_at timestamptz,
        flagged bool default false, created_at)
discoveries(player_id fk, element_id text, recipe_key text, discovered_at timestamptz,
            primary key (player_id, element_id))
recipe_finds(player_id fk, recipe_key text, primary key (player_id, recipe_key))   -- на будущее
request_log(player_id, endpoint, at)                                               -- лимиты частоты
daily_challenges(day date pk, target_element text, rules jsonb)                    -- расширение
daily_runs(player_id, day, started_at, finished_at, steps, primary key (player_id, day))
```

Доступ к таблицам из клиента запрещён полностью; клиент работает только через функции. Ключ с полными правами существует только в переменных окружения функций.

### 6.4 Отправка открытий

`POST /discoveries` с сессионным токеном и пачкой событий `{ seq, a, b, out, clientTs }` (≤ 50 за запрос). Сервер для каждого события по порядку:

1. Рецепт `a + b` существует в серверной копии контента и даёт `out`.
2. Оба входа — начальные элементы или уже подтверждены у этого игрока (с учётом событий, принятых раньше в этой же пачке).
3. Вставка в `discoveries` с уникальным ключом `(player_id, element_id)`: повтор игнорируется — **повторная отправка идемпотентна**, повторное получение известного элемента не увеличивает счёт.
4. Лимиты: максимум новых подтверждённых открытий в минуту и в час (порог правдоподобного темпа человека), лимит запросов на игрока и на токен, ограничение размера пачки.
5. `score` = число строк в `discoveries` игрока; обновляется в той же транзакции. При равенстве очков выше тот, кто достиг их раньше (серверное время).
6. Ответ: принятые / отклонённые события с причинами. Клиент удаляет принятые из очереди, отклонённые помечает (не повторяет бесконечно).

Время всегда серверное; `clientTs` используется только для диагностики.

### 6.5 Чтение

`GET /leaderboard?scope=global&limit=50` + позиция игрока и соседи. Кэширование ответа 30–60 с. Ежедневный рейтинг — `scope=daily&day=YYYY-MM-DD`.

### 6.6 Честные ограничения защиты

- Комбинации детерминированы и рано или поздно появятся в открытых справочниках. Сервер гарантирует, что каждое открытие **допустимо** (рецепт существует, предпосылки открыты, темп правдоподобен), но не может доказать, что их совершил человек, а не скрипт, знающий дерево рецептов и работающий в «человеческом» темпе.
- Максимальная выгода такой накрутки ограничена: очков не больше, чем элементов в игре, а скорость сдерживается лимитами.
- Мультиаккаунты ограничены необходимостью аккаунта Яндекса.
- Дополнительно: пометка аномалий (`flagged`) и скрытие из рейтинга без удаления прогресса.
- Продуктовый риск: при полном прохождении многие игроки упрутся в максимум, и верх таблицы станет плоским. Смягчение: тай-брейк по времени достижения, регулярное добавление контента, ежедневные испытания.

### 6.7 Ежедневные испытания (расширение)

Сервер публикует испытание дня (целевой элемент, правила, ограниченный стартовый набор). `POST /daily/start` фиксирует серверное время старта, события испытания проверяются тем же механизмом в изолированном контексте дня, `finish` — по серверному времени. Рейтинг — по числу шагов или времени. Структура таблиц заложена в §6.3, реализация — после выпуска основной игры.

### 6.8 Поведение клиента

- Очередь `outbox` хранится в сохранении и переживает перезапуск.
- Отправка с экспоненциальной задержкой, только когда есть сеть и сессия.
- Ошибки сети и сервера показываются ненавязчиво; алхимия никогда не ждёт ответа сервера.

Vite + TypeScript strict, ESLint, Vitest, Playwright, CI, `platform/local` и `platform/yandex` (только init/ready/pause), скрипт `pack-yandex`.
**Готово, когда:** `npm run build` и `npm run pack` создают ZIP с `index.html` в корне, без пробелов и кириллицы в именах, < 100 МБ (проверяется скриптом); страница открывается через `sdk-dev-proxy --dev-mode`, `LoadingAPI.ready()` вызывается после отрисовки; CI зелёный.

### Этап 1. Ядро алхимии и контент-конвейер
Схемы, компиляция, валидатор, индекс рецептов, `combine`, прогресс, события. Стартовая база ~40–60 элементов для проверки механики.
**Готово, когда:** unit-тесты покрывают: перестановку входов, упорядоченные рецепты, комбинацию с собой, несуществующую комбинацию, повторное открытие (счёт не растёт), альтернативный рецепт, секретные элементы; для каждого правила валидатора есть сломанная фикстура, на которой он срабатывает, и чистая база проходит; `content:check` в CI.

### Этап 2. Лаборатория: поле, палитра, перетаскивание
DragController, касание-касание, палитра с поиском и категориями, обратная связь (успех, неудача, новое открытие), адаптивная вёрстка, заглушки иллюстраций в едином стиле.
**Готово, когда:** e2e на ПК (мышь) и мобильной эмуляции (touch) проходят сценарии: перенос из палитры, соединение, неверная комбинация, удаление, повторное получение; на всех размерах из §3.4 нет прокрутки страницы, выделения текста, контекстного меню, элементы не выходят за экран; ручная проверка на реальном телефоне.

### Этап 3. Сохранения
Локальное сохранение, миграции, облачное через SDK, слияние, обработка повреждений, офлайн.
**Готово, когда:** тесты: перезагрузка сохраняет всё (открытия, рецепты, дневник, настройки); слияние двух расходящихся снимков не теряет открытий; повреждённый JSON не обнуляет прогресс; при недоступности облака игра работает; e2e «открыть → перезагрузить → прогресс на месте».

### Этап 4. Энциклопедия, дневник, настройки, звук, локализация
Энциклопедия (найденные рецепты, счётчики альтернатив, описания), архитектура дневника (страницы, поля, формулы, подсказки) с несколькими тестовыми записями, настройки, пауза платформы, ru/en.

### Этап 5. Онлайн-рейтинг
После ответов на вопросы 1–3. Сервер (функции, миграции), обмен подписи на сессию, отправка открытий, чтение таблиц, никнейм, UI рейтинга, очередь.
**Готово, когда:** серверные тесты: поддельная или чужая подпись отклоняется; невалидный рецепт, отсутствующая предпосылка, превышение темпа отклоняются; повторная отправка идемпотентна; смена никнейма сохраняет `player_id` и очки; запись в таблицы напрямую из клиента невозможна (проверка политик); клиентские тесты: обрыв сети → события в очереди → отправка после восстановления, игра не блокируется; в клиентской сборке нет серверных секретов (автоматический поиск по бандлу); проверка на реальном черновике игры через dev-proxy с CSP.

| Риск | Последствие | Решение |
|---|---|---|
| Секретный ключ подписи доступен только после подключения покупок | Без него сервер не может проверить личность игрока, рейтинг с серверной проверкой невозможен | Выяснить условия подключения покупок (вопрос 2); до этого — этапы 0–4 |
| CSP Яндекс Игр блокирует запросы к своему серверу | Рейтинг не работает в продакшене | Запрос в поддержку до модерации; проверка через `sdk-dev-proxy --csp` |
| Персональные данные (идентификатор Яндекса, никнейм) на зарубежном сервере | Юридический риск | Склонность к Yandex Cloud; при выборе Supabase — консультация юриста |
| Оплата Supabase из РФ | Нельзя перейти на платный тариф; бесплатный приостанавливается при неактивности | Yandex Cloud или осознанный выбор Supabase Free на старте |
| Детерминированные рецепты публикуются фанатами | Накрутка в «человеческом» темпе | Ограничения описаны в §6.6; не обещать абсолютной защиты |
| «Потолок» рейтинга | Плоская вершина таблицы | Тай-брейк по времени, обновления контента, ежедневные испытания |
| Объём контента и иллюстраций | Главный риск по срокам | Конвейер с заглушками, раннее согласование стиля и формата |
| Документация Яндекса проверена косвенно | Возможны неточности в лимитах и деталях API | Перед этапами 5 и 7 сверить отмеченные [проверить] пункты на живых страницах |
| Пользовательские никнеймы | Оскорбительные имена, претензии модерации | Фильтр, ограничение частоты смены, возможность скрыть имя |

## 10. Вопросы, требующие решения

1. **Платформа сервера рейтинга:** Yandex Cloud (рекомендую) или Supabase? Нужен ли вам доступ к данным в РФ?
2. **Подключение внутриигровых покупок** в консоли Яндекс Игр — возможно ли для вас (это условие получения секретного ключа)? Продавать что-либо не обязательно, ключ нужен для проверки игрока.
3. **Рейтинг только для авторизованных игроков Яндекса?** (Рекомендую да: иначе нет стабильной проверяемой личности.)
4. **Языки на запуске:** только русский или русский + английский? (Рекомендую оба: архитектура одинакова, стоимость — тексты.)
5. **Объём контента к первому выпуску:** ориентир по числу элементов (например, 150–250)? Влияет на объём иллюстраций и сроки.
6. **Иллюстрации:** кто и в каком формате будет их создавать (растр/вектор, размер)? До их появления я сделаю единообразные заглушки в стиле туши на пергаменте.

Вопросы о монетизации (реклама, подсказки за просмотр) можно отложить до этапа 6.
